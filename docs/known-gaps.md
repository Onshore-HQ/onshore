## Must close before real customer data goes in

- **An independent penetration test.** See `pentest-report.md`.
- **Support adapters against live accounts.** Freshdesk and Intercom follow their docs in part. Zoho Desk and Salesforce come from general API knowledge, because their docs could not be read. All four are tested only against mocks.
- **Identifier lists.** See `identifier-rules.md`: the institution list is third-party, and no NIMC or NIBSS specification was reachable.
- **Performance on real hardware.** On a laptop at 10 concurrent clients, tokenize p95 is 37 to 43 ms against a 30 ms target and detokenize 22 to 33 ms. The log processor target has not been tested on 2 cores. See `performance.md`.
- **Node SDK on Node 26.** The default `fetch` sends one request at a time, which caps a process well below what the product can do. See `performance.md`.
- **Mobile SDKs on real devices.** See `mobile-sdks.md`: no phone has run any of them, and on iOS only a simulator has.
- **Your signed legal documents.** Enter the adopted scope and each flow's transfer ground in the console. The product assumes nothing.

- **Publishing a value list on a slow machine.** When the 100,000-value benchmark runs for more than about 60 seconds, publishing fails with `vault_unavailable`: the vault does not crash, and the connection is cut before it answers, though the code allows 5 minutes. **The cause is not found.** Raising the write limit on that route did not fix it. It failed on most full runs while the laptop was in heavy swap, and passed on others.

## Detection limits worth knowing

- **A bare 11-digit number after a word like `order`, `ref`, `ticket` or `invoice` is not flagged in traffic.** A real BVN written that way passes, and so does a phone number, including in `{"ref": ...}`, `ref="..."` in XML, and `?ref=` in a query. This is deliberate: those words are usually right, and flagging them all would redact genuine order numbers. An explicit cue such as `BVN` wins. Decided 2026-11-04: the default stays, and a customer who wants these caught publishes the custom entity in `custom-entities.md`. That rule is tested in the detection engine only (`TestBareNumberAfterBusinessWordRecipe`), not through a live proxy route.
- **Purposes are stricter than traffic.** Any run of ten or more digits in a purpose becomes `[number removed]`, so a long ticket number is lost from the audit log. That is the trade for a log that is exported and permanent.
- **Card numbers:** a Luhn-valid number on a known card range is treated as a card whatever word comes before it. Other card-shaped numbers can still be excused by those words.

**Not built:**

- **Per-entity runtime timing**, and the console flag for the slowest 5%. Only the publish-time benchmark exists.
- **Automatic re-hashing of value lists.** This product has no blind-index key rotation, so nothing would trigger it. Uploads are kept encrypted for 30 days and then purged, as the spec says, but nothing reads them yet.
- **"What each role would see"** on the Policies tab. It lists the policies that reference the entity, and points to the policy simulator.

**Differs from the spec, on purpose:**

- **Value lists may cost up to 1 ms per KB, not 0.3.** The spec gives both figures. A real list measures about 0.26 ms, and one with four-word entries would pass 0.3.
- **An approved edit keeps its status.** The spec says a version goes live in shadow. Applied to an edit, that would stop enforcing the moment someone fixed a typo. New entities do start in shadow.
- **A shadow or pass entity cannot hide a built-in match**, which the spec's longer-span rule would otherwise allow.
- **An uploaded list waits for approval**, like any other change.
- **A separate list key**, derived from the blind-index key, so services that match lists never hold that key.
- **Support adapters and file redaction follow the API action**, since the spec's four modules do not name them.
- **Roles, not permissions:** `detection_manager` and `detection_approver`, as this product has no permission layer. The spec's SQL became text ids and CHECK constraints, plus a publish-requests table it did not list.

**Starter templates are not confirmed against FIRS, CAC, FRSC, INEC, NIS or NIBSS**, though the spec requires that before shipping. They ship marked Unconfirmed, and the patterns are educated guesses. Remove them, or confirm each one, before a customer relies on them.

**Also not covered:** labelled samples in Pidgin, upgrading an install that already has data (every run was a fresh install), and non-ASCII case folding in keywords, so `É` and `é` do not match each other. A format-preserving custom token looks like a real value by design; only unit tests cover it.

## Limits of what was built

- **Person names.** Dictionary, context and name-part heuristics, not a named-entity model, which would need training data the spec rightly forbids taking from customers.
- **File redaction.** Text only: no faces, signatures or stamps. OCR misses are possible on poor scans, and such files are flagged as low confidence. Speech is untested on Nigerian accents or Pidgin; it uses Whisper's English base model.
- **Support tools.** A ticket has already passed through the vendor once before the webhook fires. Intercom's text cannot be edited, so it is redacted and re-added as a note.
- **SSO.** Tested against Keycloak only. Entra sends group IDs, not names, so its mappings use IDs. With groups mapped and a groups claim named, a provider that sends no groups means "no groups", and the person is refused. Single logout and IdP-initiated sign-in are not built.
- **Detection next to a dash.** A number straight after a segment made only of hex characters, such as `abc-22333444558`, is treated as part of an ID and not detected. That guard protects UUIDs. Discovery report locations are not affected, since they remove all long digit runs.
- **Dashed card numbers.** The held-out set (20/22) still misses `5399-8312-3456-7894`, and still wrongly flags the digits in `20261103123.log`.
- **Audit.** Between signed daily checkpoints, someone with database owner rights could rewrite recent events unless a SIEM copy is configured.
- **Rate limits.** Per process and per replica.
- **OpenAPI.** Hand-written, and it does not yet list the file and support endpoints. No Postman collection.
- **Certificates.** The internal CA lasts 10 years and its key is discarded, so renewal means re-running `rv init` for certificates. There is no rotation tool yet.
- **Cloak settings and digital twins.** Places are found from a fixed list of states, cities and well-known neighbourhoods, case-sensitive; street addresses such as "12 Admiralty Way" are not. A stand-in name is restored only when the model writes it as given (or its first or last name alone), not in capitals or misspelt. Ranges, age bands and states cannot be swapped back, by design. Twins are not linked to a customer record, so erasing a customer does not delete their twins; they expire (at most 365 days) or are deleted by id. Setup export does not yet carry cloak settings. Medical and other free-text generalising, which InCountry does with a model, is not built.
- **Countries.** No country is assumed: an install's country comes from `rv init --country` or setup, each vault names its own, and a context with no vault checks every pack. All 16 packs have detectors, with the issuer's check digit where one is published. Ghana, Qatar and Egypt publish none, so those IDs are checked on structure (prefix and nationality code, century, birth year and ISO nationality code, birth date and governorate) and the bare-number ones need a word such as "ID" nearby. Names come from a dictionary of common names across all regions, not a named-entity model. Places cover each country's main divisions, cities and districts, not every street or town. Mobile, landline and any "+" international number are found; national landline formats need a word such as "phone" nearby. Everything has been tested with made-up values, not real traffic from these countries.
- **Time zones.** The organisation has a time zone, and each vault can have its own (Settings, Locations and laws); a vault without one uses the organisation's. A vault's zone decides where its day ends in usage and the residency map. Access rules with office hours and the signed audit chain use the organisation's zone, because a rule and the chain cover the whole organisation. Changing a zone moves day boundaries from then on; days already signed stay as signed.
- **Linked installs (Enterprise) and Cloud regions.** A member install joins with a single-use code (`rv init --country gb --join … --primary https://…`), then sends a signed report every minute: vault names, settings and counts, never values. The primary queues "create a vault" instructions, which the member carries out. Not built yet: one sign-in across installs (people sign in to each install's console separately), sending access rules or detection rules to members, and a combined audit view; each install keeps its own audit chain. If a member stops reporting, its vaults show as "Not reporting" after five minutes and nothing else happens. Cloud regions use the same mechanism; which regions are open is `RV_CLOUD_REGIONS`, and opening one (servers, keys, on-call in that country) is operations work, not code. Tested over real HTTP against one stack acting as both sides, not across two machines.
- **French.** Every console string has a French entry, written by us and not yet reviewed by a native speaker or a French-speaking lawyer. Laws, pack and data-type descriptions sent by the control API, error messages from the API, emails and the PDF report are still English. Numbers and dates keep the English format. `node console/scripts/i18n-wrap.mjs --check --strict` fails if a new string has no French.
- **Installing with your own public certificate** (`RV_TLS`) has not been exercised.
